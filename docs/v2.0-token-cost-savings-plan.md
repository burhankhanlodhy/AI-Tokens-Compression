# V2.0 Token and Cost Savings Plan

Status: proposed execution plan; product scope ratification required before implementation
Sources: `token-savings-technique-research.md` (reconstructed sourced research, 2026-09-19) and `product-spec-v2.md`

## Executive plan

Build V2.0 by composing independently measurable savings levers, not by claiming one headline percentage. Preserve the existing lossless L1 and output-conciseness evidence and publication rules; make provider-native caching visible and correctly attributed; retain semantic caching behind its existing tenant-safety/calibration QA gate; and investigate model routing/cascades as the principal new savings capability. Routing stays off by default unless a separately approved quality and cost evaluation passes. A gateway/provider-count feature is not itself a savings method.

The research figures are market context, not project acceptance criteria. Vendor claims and benchmark results must not be presented as directly comparable. Do not alter the ratified 57.71pp output-conciseness headline, its population, or its evidence; do not claim semantic-cache savings before AC-PC4 is green. Keep cache, compression, and avoided-call savings separately observable and prevent double-counting.

## Research-to-product disposition

| Method / finding | Current project position | V2.0 action |
|---|---|---|
| Provider-native caching | Phase A exact-prefix caching is in the product spec; provider-native discounts do not reduce tokens | Audit each supported provider's cache controls and returned usage/pricing fields. Improve prefix hygiene/documentation and expose measured cache-hit savings separately from compression. No assumed cache discount or inferred hit. |
| Prompt compression | Lossless L1 structural cleanup is the endorsed Phase B lane; output conciseness has a tightly gated benchmark/publication contract | Preserve both lanes and their existing gates. Extend only with fixture-backed, per-category evaluation and net-cost attribution; no imported LLMLingua/vendor headline and no lossy compressor enablement without parity evidence. |
| Semantic caching | Phase C-1 on pgvector is already specified and gated, with cross-tenant, false-hit, invalidation, latency and attribution checks | Treat as an existing V2 capability/gate, not a new implementation. Keep disabled until QA verifies AC-PC4 and the product's ratified calibration point. |
| Routing / cascades | Research identifies it as a major savings lever; current spec does not include routing | New, opt-in/off-by-default evaluation and implementation proposal. Measure per-request quality risk and total cost against a fixed workload; no probabilistic savings claim as a guarantee. Product scope ratification precedes implementation. |
| Gateway breadth / observability | Competitive context, not a savings lever by itself | Use for positioning only; no gateway-parity expansion in this plan unless separately approved. |

## Work sequence and gates

1. Product manager ratifies the V2.0 scope, precise acceptance criteria, and whether routing proceeds. Keep the approved existing decisions above intact unless the owner explicitly changes them.
2. Application developer audits and closes only verified gaps in provider-native cache reporting/prefix handling and the compression paths. Preserve existing interfaces and evidence; document anything already complete instead of duplicating it.
3. Database administrator reviews the ledger and migration requirements for non-overlapping attribution of provider cache discounts, L1/compression savings, semantic-cache savings, and routing/call avoidance. No schema migration absent a demonstrated gap.
4. Application developer implements the approved routing/cascade experiment behind a server-side feature flag, if ratified. Include a fixed, committed workload, baseline comparison, cost accounting, failure/fallback behavior, and quality evaluation. Keep it disabled by default pending QA.
5. QA lead independently verifies all accepted work against its written acceptance criteria and reports GO or NO-GO with reproducible evidence. On NO-GO, keep the QA gate open and return concrete fixes; do not complete the QA gate or release ticket.
6. Only on explicit QA GO, complete the QA gate and thereby release the dependent Product Manager ticket. Product Manager performs the V2.0 release push only after independently confirming the QA handoff and exact release candidate.

## Release invariants

- No release before QA GO; a NO-GO does not unblock release.
- Features with correctness/quality risk remain disabled until their own gate passes.
- Report realized token and dollar savings from ledger/workload evidence, not market claims or fixed dashboard constants.
- Show caching, compression, and avoided calls separately; savings components must not be summed twice.
- Preserve tenant/key isolation, provider behavior, cache correctness, rollback safety, and current publication contracts.
- Product manager records any scope change before implementation; owner decisions that change architecture or risk tolerance require explicit owner confirmation.

## Kanban sequence

Product scope ratification -> provider/compression and ledger audit -> approved routing implementation -> independent QA GO/NO-GO -> Product Manager release push. QA is the hard release gate; NO-GO keeps the gate unresolved and release unavailable.
