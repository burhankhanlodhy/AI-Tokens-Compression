## 1. Scope decision (one paragraph)

V2.0 is an **attribution-and-audit release, not a new-lane release**. The release
composes the already-ratified savings levers under one non-negotiable invariant —
every savings figure is ledger-derived, separately attributable, and never
double-counted — and closes verified gaps in provider-native cache reporting and
prefix hygiene. Routing/cascades is ratified **only as a flag-off discovery
experiment**; it is NOT ratified as a shippable savings lane, a dashboard figure,
or a marketing claim in V2.0 (rationale and gate in §4).

## 4. Routing/cascades — RATIFIED AS DISCOVERY-ONLY (the PM ruling)

**What is ratified:** building the measurement instrument. A server-side
off-by-default routing/cascade experiment flag, deterministic fallback to the
normal proxy path (flag-off and routing-failure both fall back), a committed
fixed evaluation workload, total-cost accounting from actual upstream
usage/pricing, and a preregistered quality-evaluation path.

**What is NOT ratified (and therefore out of the V2.0 release):**
- Any production enablement or default-on path.
- Any routing/cascade savings figure on the dashboard, in the ledger's
  published aggregates, or in marketing copy.
- Any probabilistic savings claim presented as a per-request guarantee — the
  research's own caveat stands: RouteLLM/FrugalGPT numbers are
  benchmark-distribution results with no per-request quality floor (P-graded
  evidence, not a product contract).

**Why discovery-only rather than full ratification:** our wedge is
*lossless + verifiable* (the research's own "Us vs. them" §: we are alone on
verifiability). Routing is the largest published lever but the only one whose
quality guarantee is inherently probabilistic — shipping it as a V2.0 savings
claim would trade the one defensible differentiator for the one number we can
least honestly defend. Building the instrument now, off by default, generates
the evidence the owner needs for a real enablement decision later without
betting the release on it. This does not change architecture (additive flag +
harness, same pattern as the dose-pin and semantic-cache switches), risk
tolerance (zero user-facing behavior change), or the Phase C ruling — so it
does not meet the card's escalation bar; it is inside this card's authority.

**The enablement decision later requires, at minimum:** the committed
workload's measured quality distribution vs the fixed baseline, total-cost
accounting on real quotes, a per-request quality-floor story (or an explicit
owner acceptance that none exists), and a fresh explicit ratification. That
future decision belongs to @user.

## 5. Acceptance criteria for the downstream cards

- **AC-V2-1 (lane preservation).** L1 and output-conciseness paths are either
  untouched or changed only where a gap is demonstrated; the diff does not
  weaken AC-P1b/P1e/P1f/P1g, the corpus checksum pin, or any pinned status
  literal. QA asserts by contract-surface diff, not spot check.
- **AC-V2-2 (no market numbers in product).** No research/vendor figure
  (LLMLingua, RouteLLM, GPTCache, provider discount tables) appears in code,
  config, dashboard constants, or docs presented as our acceptance bar. Code
  review + grep gate.
- **AC-V2-3 (semantic cache untouched).** No change to the ratified PC
  design, scope keys, version-namespace policy, or operating point; the flag
  stays off; `semantic_hit` attribution rules unchanged.
- **AC-V2-4 (attribution, no double-count).** For any ledger row the release
  touches: cache savings (exact/semantic/provider-native) and compression
  savings remain separately attributable, and the decomposition invariants
  hold at every aggregation level. DBA evidence + QA reconciliation suite.
- **AC-V2-5 (release invariants).** From the plan doc, unchanged: no release
  before QA GO; risky features off until their own gate passes; realized
  savings from ledger/workload evidence only; tenant/key isolation, provider
  behavior, cache correctness, and rollback safety preserved.
- **AC-V2-6 (provider-native cache honesty).** Cache-hit savings derive from
  provider-returned usage fields actually observed on the response; a request
  with no observable cache evidence records zero cache savings; per-provider
  behavior documented in the audit notes.
- **AC-V2-7 (routing experiment mechanics).** Server-side flag, default off;
  no request header or query param can enable it (dose-pin discipline);
  deterministic fallback on flag-off and on any routing failure; committed
  workload fixture; cost figures from upstream usage/pricing, never modeled
  percentages; the experiment's outputs are evidence artifacts, not dashboard
  data.
- **AC-V2-8 (routing non-claim).** V2.0 release notes, README, and dashboard
  contain no routing savings claim; the only permitted mention is the
  flag-gated experimental capability, labeled off by default.
- **AC-V2-9 (QA is the gate).** t_037cb213's GO/NO-GO gates the release
  ticket (t_3d7ab2ef); a NO-GO leaves the release unresolved until concrete
  fixes land and QA re-verifies.

## 6. Out of scope for V2.0 (explicit)

Production routing enablement; hosted billing; new provider breadth; any
semantic-cache enablement ahead of AC-PC4; any change to the P1/P6 publication
contracts; lossy compressor enablement without parity evidence.
