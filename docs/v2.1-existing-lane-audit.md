## 3. V2.1 data-contract audit (migration 7 @ `982a284`)

Schema probes executed on a disposable pgvector container (per-store results
in §4 below; full probe log in the task's completion metadata):

- **Additive-only scope held:** the `982a284` diff is 3 files (new migration,
  MIGRATIONS.md §, docker-compose mount `48-v21-session-stores.sql`). Zero
  `requests` columns touched, zero semantic-cache/routing objects touched,
  `strategy_telemetry` carries no savings fields (non-overlapping ledger —
  ratified ruling 6).
- **Isolation (ruling 5):** every store leads its unique/lookup key with
  `tenant_id`; `tocp_continuations` is `UNIQUE (tenant_id, continuation_id)`
  so the same opaque id under two tenants cannot collide, and the lookup index
  is `(tenant_id, session_id, expires_at)`. Probes: cross-tenant insert of the
  same continuation_id succeeds; tenant-scoped retrieval returns exactly one
  row per tenant; `EXPLAIN` on the tenant/session retrieval shape uses
  `uq_tocp_continuations_tenant_id` / `idx_tocp_continuations_lookup`, no seq
  scan. `api_key_id` is nullable (session not always key-scoped) matching the
  `requests` ledger convention.
- **Retention (ruling 7):** `expires_at` is NOT NULL on all three stores with
  `chk_*_ttl_positive` (`expires_at > created_at`); purge statements are the
  documented per-store `DELETE ... WHERE expires_at <= now()` with the
  dedicated `idx_*_expiry` indexes. `strategy_telemetry` intentionally has no
  TTL (audit-style evidence, bounded by ops window per MIGRATIONS.md).
- **Bytes authoritative (semantic_cache_responses convention):** verbatim
  originals in BYTEA with `chk_*_content_digest` (sha256 format + digest()
  match) and `chk_*_content_length` (octet_length equality). JSONB is used
  only for lane-specific telemetry evidence, never for originals.
- **Tenancy FK class:** `ON DELETE CASCADE` from tenants/api_keys matches the
  `cache_entries` disposable-derived-state class, not the `requests` RESTRICT
  audit class — consistent with MIGRATIONS.md's stated disposability ruling.
- **Rollback:** documented DROP of the four tables in one transaction
  restores the pre-V2.1 request path byte-for-byte (no requests columns or
  constraints modified). Executed in probes: rollback → 0 V2.1 tables remain
  → re-apply clean.
- **Idempotency / fresh-vs-existing volume:** `CREATE TABLE IF NOT EXISTS` +
  `CREATE INDEX IF NOT EXISTS` + `CREATE EXTENSION IF NOT EXISTS pgcrypto`;
  re-apply verified clean with row survival (same convention as migrations
  5/6). Compose mount is last in initdb order (48-), after 47-v2.

## 4. Checks delivered by this package (acceptance mapping)

New committed tests (both Postgres-backed, pgvector lane compatible, skip
cleanly when `TOKEN_SAVER_PG_BASE` is unset — the established
`pg_test_support` convention):

`test_v21_session_stores_migration.py`
1. fresh-volume sequence: base schema → migration 7 (ON_ERROR_STOP semantics;
   pgcrypto required for digest CHECKs);
2. existing-volume sequence: migration 7 applies over a pre-V2.1 base with no
   V2.1 objects present, idempotent re-apply, rows survive;
3. wiring: Compose initdb mount `48-v21-session-stores.sql` present and
   ordered after `47-v2-provider-cache-usage.sql`; migration file registered
   in MIGRATIONS.md as entry 7;
4. constraint rejection matrix: bad sha256 format, digest mismatch,
   content_length mismatch, negative/zero TTL, empty session_id /
   continuation_id / tool_name / result_status / canonical_path / version_id
   / role / strategy / decision, bogus relevance_tier, negative turn_index,
   duplicate (tenant, session, turn_index), bad telemetry decision, negative
   latency, bad segment_bytes — per store, each rejected;
5. valid-insert acceptance per store (happy path survives all CHECKs);
6. cross-tenant isolation: same continuation_id under two tenants, tenant-
   scoped retrieval returns exactly one row each; plan uses the tenant-led
   index; cross-session retrieval returns nothing;
7. TTL expiry purge shape: `DELETE ... WHERE expires_at <= now()` empties
   expired rows only (unexpired rows survive) per store;
8. rollback compatibility: documented rollback removes exactly the four V2.1
   tables; `requests` schema (columns, `chk_route`, `chk_cache_status`,
   `chk_*` taxonomy) byte-identical before/after; re-apply after rollback
   clean; ledger rows written pre-rollback still present and readable with
   V2.0 attribution intact;
9. cascade check: deleting a tenant empties its session-store rows while the
   `requests` FK RESTRICT behavior is unchanged.

`test_v21_strategy_attribution_reconciliation.py` (reconciliation fixture for
new strategy evidence — row/bucket/provider/tenant/key decomposition):
10. strategy_telemetry is evidence-only: writers can record every ratified
    lane/decision combination with per-lane metadata JSONB, and no savings
    fields exist to double count (column list pinned by assertion);
11. no-double-counting decomposition probe: one ledger row with all five V2.0
    attribution fields set simultaneously (cache_savings, l1_savings,
    tool_compression_saved, provider_cache_read/write_tokens) plus V2.1
    strategy_telemetry rows for the same request — aggregation at row, day
    bucket, provider, tenant, and key levels independently recomputes each
    addend and proves no field is derivable from summing the others
    (hand-computed expectations, independent of SQL under test, per the
    test_kpis convention);
12. telemetry rows never alter ledger reconciliation: KPI overview/series
    totals are identical with and without V2.1 telemetry rows present.
