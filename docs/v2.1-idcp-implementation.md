# IDCP implementation boundary

`proxy.idcp` implements the V2.1 file-context primitives and Postgres immutable
version ledger. Call `IDCPStore.read` inside a Postgres transaction with a
`FileScope` built from trusted authenticated tenant, API-key, and session state.
The `enabled` argument is deliberately false by default; the caller must use the
server-side `v21_idcp_enabled` policy decision before passing `enabled=True`.
No request header or request-body value may set that deployment flag.

A first read returns full bytes and appends a version row. A repeated hash
returns an explicit unchanged record. A changed text file returns a unified
diff only when it is smaller than the full new file, within the absolute cap,
passes the optional validation callback, and the expected base still matches.
Otherwise the result contains full bytes and an explicit fallback reason. Each
diff identifies canonical path and base/new immutable version IDs. Writes are
serialized per scope/path with a transaction advisory lock; the ledger query is
scoped by tenant, API key, session, and canonical path. The caller owns the DB
transaction and must commit/rollback the version insertion together with its
request state.

Deletion is a non-patch `deleted` notice and rename inference is intentionally
unsupported: a path not previously seen is a full first read. The schema stores
immutable file contents but has no tombstone column, so deletion notices are
not persisted as versions. Do not try to apply a deletion notice as a diff.

The existing chat-completions request body has no trusted file-path/version
contract. This implementation therefore does not infer paths from arbitrary
prompt/tool text or modify the V2.0 forwarding path. It is a callable backend
primitive until an authenticated caller contract is ratified and paired replay
inputs are available. The deployment flag remains off by default.

The tests include deterministic first/unchanged/change/fallback/deletion/rename/
stale/validation/path handling, reconstruction, DB-scope SQL assertions, and an
offline tokenizer comparison for repeated file context. `benchmark/idcp_replay.py`
adds a reproducible, explicitly synthetic 50-session provisional replay (150
localized edits): 137,700 baseline repeated-file tokens versus 17,250 IDCP
representation tokens with the `gpt-4o` tokenizer (87.4728% reduction); zero
silent stale applications in the harness. This is not representative task
traffic, does not include whole-session overhead or task outcomes, and therefore
cannot establish the ratified >=30%/<=3pp acceptance gate. Task-success
regression remains unmeasured; do not claim the empirical gate passed. The
caller remains unintegrated because there is no trusted file-path/version
contract, and the lane stays default-off pending contract ratification and QA.
