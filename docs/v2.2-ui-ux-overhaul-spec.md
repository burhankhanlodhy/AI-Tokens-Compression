## 0. What this spec decides (and what it deliberately does not)

This spec decides PRODUCT SCOPE: the page inventory, what is runtime-configurable vs deployment-only, which compression controls are safe to expose, secret-handling constraints, the data/API contracts, and measurable acceptance criteria.

It does NOT decide visual design, layout, or interaction patterns — those belong to @ui-ux-engineer. Where this spec says "OPEN DECISION — design owner", the design card resolves it within the stated constraints.

### 1.2 Frontend architecture (what a redesign inherits)

- Shell: `proxy/dashboard_v2.py` — one Python string template, dark theme, 12-col grid, Chart.js **from CDN** (dashboard_v2.py:19).
- Logic: `proxy/static/dashboard.js` (~770 lines, plain ES5-style IIFE, no framework, no build step). Hash-based tab routing (`#overview|#traffic|#providers|#keys`), bucket selector injected into nav (dashboard.js:764-768).
- Data discipline (invariant, must be preserved): every displayed NUMBER is read 1:1 from `/api/kpis` (SQL-side aggregation, kpis.py) or `/api/keys|/api/tenants` — zero client-side aggregation (AC-A8; dashboard.js:1-2). Savings decomposition tiles are contained sub-tiles, never summed into the headline (a1eae90 contract; dashboard.js:35-63). Semantic-cache mode badges ("off"/"warming"/"live") are modes, never measurements (dashboard.js:75-101).
- Testability: `token-saver/test/dashboard_render_harness.js` + `test_dashboard_render.py`, `test_keys_tab_render.py`, `test_semantic_cache_dashboard_render.py` run the JS against fixture payloads in CI (Node 22 in .github/workflows/ci.yml). Any new frontend MUST remain testable in this harness or the design card must explicitly spec a replacement harness.

### 1.3 Data layer

- Dual ledger: Postgres when `TOKEN_SAVER_PG_DSN` is set, else SQLite (stats.py:156-176). Postgres schema: postgres-schema-v2.sql (tenants/providers/api_keys/requests/cache_entries + backfill_batches); migrations mounted by docker-compose.yml (7 SQL files, including 20260924_v2_provider_cache_usage.sql and 20260924_v21_session_stores.sql).
- /api/kpis (kpis.py) is the single aggregation surface: overview, cache (exact + semantic taxonomy), series, by_model, by_provider, latency percentiles — all SQL-side, tenant_id/api_key_id scoped before aggregation (AC-A7, kpis.py:45-54).
- SQLite /stats path (stats.aggregate_stats) is a SEPARATE older surface that does not carry cache_status, dose_tier, provider attribution, or tenant scoping.

### 1.4 Configuration (proxy/config.py)

All settings are env/.env-backed via pydantic-settings (`Settings`, config.py:21-286); `get_settings()` is `@lru_cache`d (config.py:346-349) — there is NO runtime persistence and NO runtime mutation path today. Feature flags span lossless transforms (l1_enabled, tool_schema_minify, tool_result_compression_enabled — all default ON) and risky lanes (V2.1 v21_*_*_enabled — all default OFF, config.py:42-49). `ADMIN_TOKEN` may be generated at boot and printed once (main.py:180-195).

### 1.5 Gaps and latent defects found by this audit (must be addressed or explicitly deferred)

- **G1 (dead trusted scope):** `request.state.tenant_id` / `request.state.session_id` are READ in main.py:675-676, 1654-1656 but NEVER SET anywhere — no middleware, no dependency populates them (verified: no assignment exists in proxy/ or set in tests' live path). Consequence: TOCP continuation (main.py:682-697) and `/v1/tool-results` are unreachable-dead in production, and strategy_engine.PolicyContext can never validate scope from the live request path. V2.2 persistence work must either wire authenticated proxy-key → tenant/session resolution or document the lane as benchmark-only.
- **G2 (unauthenticated management reads):** GET /api/tenants and GET /api/keys expose tenant/key inventory with no auth (writes are ADMIN_TOKEN-gated). Same for /api/kpis and /api/tripwire. Product ruling: acceptable for self-host default, but the Settings tab must NOT widen exposure further, and the spec requires a written threat-model note in the design card.
- **G3 (admin token UX):** with no ADMIN_TOKEN configured, the operator must read a one-time boot-log token (main.py:194). The new Settings tab must support this flow explicitly (paste-once, in-memory only — matching dashboard.js §4.5 discipline: module variable, never storage/URL/log).
- **G4 (two stats surfaces):** /stats (SQLite, legacy) and /dashboard (Postgres KPIs) disagree by construction when the PG ledger is authoritative. Ruling in §3.4.

## 2. Approved information architecture & page inventory

Keep the single-page shell + hash routing model (constraint: no build toolchain in CI today; Node 22 is available only for the render harness — a framework migration is a non-goal, §7). Five tabs:

1. **Overview** (exists, evolve): headline KPIs (requests, tokens saved, est. cost saved, savings %), savings decomposition sub-tiles (L1 / exact cache / semantic cache — modes not measurements), savings-over-time chart, per-model donut, recent buckets table. PRESERVE the a1eae90 decomposition contract verbatim.
2. **Traffic** (exists, evolve): latency p50/p95/p99 + avg, requests/errors per bucket, error rate, cache status taxonomy badges (verbatim ledger statuses per cache-status-dashboard-spec §4.3). Add: per-route split (compress vs passthrough) — requires the new `/api/kpis` `by_route` series (§5.3, currently dropped at main.py:1719-1720 deliberately; re-adding is a backend contract change, in scope).
3. **Providers** (exists, evolve): per-provider traffic/savings/error cards from `by_provider`. Add: provider REGISTRY facts (name, base_url, adapter_class, enabled) surfaced from the seeded `providers` table via a new read endpoint (§5.3). Registry rows are configuration, not secrets — base URLs are displayable; credentials are not (§4).
4. **Keys & Tenants** (exists, preserve semantics): tenant card, per-key table with rotate/revoke confirms, one-time reveal, per-key usage drawer, ADMIN_TOKEN prompt. All existing C10 redaction and §4.5 token rules carry forward unchanged.
5. **Settings** (NEW — the core of V2.2): see §3. Renders the runtime-configurable controls (§3.1), the read-only deployment inventory (§3.2), the V2.1 strategy flag audit (currently only at /api/strategies), and the tripwire status (currently only at /api/tripwire) so operators stop needing raw JSON endpoints.

**Legacy surfaces:** /stats and its server-rendered renderer stay untouched in V2.2 as a compatibility surface (non-goal to remove); no redesign work, no new features. It is a release blocker to break either of them (§8).

## 3. Settings model — runtime-configurable vs deployment-only

### 3.1 Runtime-configurable (persisted, ADMIN_TOKEN-gated writes, effective without restart)

Product ruling: exactly these controls are safe to expose at runtime, chosen because each is (a) lossless or independently benchmarked, (b) already switchable per-deployment without ordering hazards, and (c) harmless mid-flight (the request path reads settings at request start):

| Control | Setting today (config.py) | Default | Rationale |
|---|---|---|---|
| L1 structural cleanup | l1_enabled | ON | Lossless, corpus-pinned (B-26/B-28 contract tests). |
| Tool-schema minification | tool_schema_minify | ON | Lossless on validated schemas; failure path keeps verbatim (main.py:652). |
| Tool-schema cache | tool_schema_cache_enabled | ON | Sub-switch of cache_enabled; no wire-shape risk. |
| Tool-result optimization | tool_result_optimization | ON | Output-side only; assistant envelopes byte-preserved (main.py:667-672). |
| Tool-result compression | tool_result_compression_enabled | ON | Lossless tool-result class only. |
| Output conciseness | output_conciseness_enabled | OFF | Benchmarked net-negative on short prompts (P1-1 PM decision); per-request header override already exists and keeps precedence over the runtime default. |
| Semantic cache | semantic_cache_enabled | OFF | Deployment-gated today; becomes runtime-visible but WRITE still requires the AC-PC4/PC5 gate to be green (tripwire/calibration artifact). UI renders the gate state, not just a toggle. |

NOT runtime-exposable (deployment-only, rendered read-only in Settings): compression_enabled + LLMLingua model/rate (lossy model-backed — flipping mid-flight changes pipeline semantics and costs), provider_routing and provider_base_urls (transport-level, requires restart discipline), dose-tier calibration flags (grounded_calibration_green, allow_dose_pin, tripwire_* — PM-gated instruments, config.py:204-240), embedding_model/dimensions/cosine threshold (calibration-bound), upstream_base_url/timeout, ADMIN_TOKEN (set at boot only), measurement_tag.

### 3.2 Settings persistence & precedence (contract for @database-administrator + @application-developer)

Precedence order (highest wins), decided here so no two cards re-derive it:

1. Per-request control headers (existing: x-token-saver-conciseness, x-token-saver-dose-pin — benchmark-only, unchanged).
2. Runtime overrides (new persisted layer, Postgres `app_settings` table keyed by setting name; ADMIN_TOKEN-gated PUT; reads joined into the settings path at request start; SQLite-only deployments fall back to a JSON file next to the SQLite DB — DBA card owns the schema).
3. Environment variables (current behavior, unchanged).
4. Built-in defaults in config.py.

Requirements: every override records `updated_at` and `updated_by` (last-4 of the admin token is NOT acceptable as identity — record "admin" or the key id); overrides are auditable via a GET that returns value + source (runtime|env|default) per setting; deleting an override reverts to env/default immediately; unknown setting names are rejected 400; the effective-value endpoint is what the UI renders, never the raw overrides table alone.

### 3.3 Compression controls — what the UI may claim (product constraint, binding on design)

The dashboard may never present an estimated-savings number that the ledger does not back. Concretely: tool_compression_saved is attribution-only and NOT additive with L1 totals (stats.py:35, postgres-schema-v2.sql:96); L1 and cache savings are never summed on one request (main.py:1250-1258); provider-native cache usage (provider_cache_read/write_tokens) is measured evidence only, never merged into savings. V2.2 may ADD display surfaces for these fields but must preserve the "contained, never summed" rule (a1eae90) for every new tile, and semantic-cache mode badges stay modes (off/warming/live), never 0% presentations of stale windows.

### 3.4 Provider/API-key requirements & secret handling (binding)

- BYOK is invariant: upstream credentials pass through per request (main.py:363-368) and are NEVER stored, displayed, or persisted. The Providers tab shows base URLs/adapter facts only — any upstream-key field in a design mock is a spec violation.
- Proxy-facing keys: sha256 hash + last4 only (api_keys table, postgres-schema-v2.sql:57-69); plaintext revealed exactly once at create/rotate (main.py:1845-1890; dashboard.js reveal panel). Preserve C10 redaction in every new surface.
- ADMIN_TOKEN: bearer on all writes AND on the new settings PUT (§3.2). Module-variable-only in the browser (dashboard.js:334, 715). G3 flow (boot-printed token) must be first-class in the Settings tab.
- G2 ruling: reads stay unauthenticated for self-host, BUT the design card must include a threat-model note, and if hosted multi-tenant mode is ever detected (tenants.plan != 'self_host'), the Settings and Keys tabs must surface a "restrict reads" warning banner. (Enforcement of read-auth is a non-goal for V2.2, §7.)

## 4. User workflows & priority states

Priority order (P0 first). Every screen must define loading (skeleton), empty (per-tab copy — the keys tab's "No proxy keys yet" pattern, dashboard.js:517), error (inline error + retry, never a re-render that loses form/confirm state — dashboard.js §4.4), and degraded (ledger 503 → per-card degradation, not a full-page failure) states.

- **P0 — Operator sees savings honestly:** Overview renders ledger-backed numbers with decomposition intact; ledger outage fails loudly (503 → error state), never silent zeros (main.py:1721-1734 rule extends to the UI).
- **P0 — Operator manages proxy keys safely:** existing rotate/revoke/create/reveal flows unchanged; confirm states survive a 401 re-prompt (dashboard.js §4.5.4).
- **P1 — Operator changes settings without a restart:** Settings tab toggle → PUT override → effective value reflected; an env-set value shows source "env" and a runtime override shows "override" with a clear revert path; admin token prompt appears on 401 exactly like keys writes.
- **P1 — Operator understands pipeline state:** strategy flags (from /api/strategies) and tripwire status (from /api/tripwire, including its pending_calibration / pending_metric_ruling states, tripwire.py) rendered as status cards, not raw JSON.
- **P2 — Operator sees per-route and per-provider attribution:** Traffic by_route split; Providers registry facts + provider-native cache usage columns (§3.3).
- **OPEN DECISION (design owner):** responsive behavior below 900px today only re-spans grid columns (dashboard_v2.py:109). Design card decides the mobile IA (tab bar vs overflow) within the no-framework constraint.

## 5. Data / API contracts

### 5.1 Unchanged (the floor)

GET /api/kpis (contract + param validation, kpis.py:294-329), /api/tenants, /api/keys (+writes), /api/strategies, /api/tripwire, /metrics, /health keep current shapes. Frontend changes must not require breaking these.

### 5.2 New: settings API (backend card; DBA card owns storage)

- GET /api/settings → {settings: [{name, value, source: "runtime"|"env"|"default", category: "runtime_configurable"|"deployment_only", updated_at?}]} (ADMIN_TOKEN for PUT; GET unauthenticated per G2 ruling).
- PUT /api/settings/{name} {value} → 200 updated | 400 unknown/not-runtime | 401. DELETE /api/settings/{name} reverts.
- Only §3.1's allowlist is runtime-writable; the allowlist lives in code (config.py or a settings module), is testable, and is the QA gate surface.

### 5.3 Extended /api/kpis and new registry read (backend card)

- Add `by_route` series to /api/kpis (SQL GROUP BY route — column exists in both ledgers).
- GET /api/providers → registry rows (name, base_url, adapter_class, enabled) + aggregated per-provider KPIs joined in the same response (or keep by_provider in /api/kpis and make this registry-only — implementation card picks one; the UI contract is: registry facts + per-provider KPIs both reachable).
- All new read endpoints follow the existing conventions: 503 ledger-unavailable envelope (kpis.py:321-328), 400 field-named param errors (B-10, kpis.py:285-291).

### 5.4 G1 resolution (required for Settings/pipeline surfaces to be honest)

The persistence card must wire authenticated proxy-key requests to tenant/api-key/session context (api_keys.key_hash verification against the caller's `Authorization: Bearer tsk_…`) OR the product ratifies "trusted scope = benchmark-only" and the UI labels TOCP/session lanes accordingly. Decision needed BEFORE the implementation card; default if unresolved: label session-bound lanes "benchmark scope — not enforced on live traffic" (honest, matches current reality).

## 6. Configuration & persistence expectations (summary)

- Restart safety: runtime overrides survive proxy restart (Postgres row / SQLite JSON file), env vars still win over nothing (precedence §3.2), built-in defaults are the floor.
- The dashboard MUST surface the source of every displayed setting value — an operator must never have to guess whether a toggle is runtime, env, or default.
- Docker: docker-compose.yml gains nothing new except the settings table arrives via the mounted-migration pattern (48-* sequence) — DBA card owns the migration file and docker-compose mount order.

## 7. Explicit non-goals

1. No frontend framework, no bundler, no npm build step in CI (render-harness testability is mandatory).
2. No removal or redesign of /stats legacy surface; no new features there.
3. No hosted multi-tenant UI (tenant picker stays deferred — keys-tenants-tab-spec §2.1).
4. No read-auth enforcement on management/KPI endpoints in V2.2 (documented threat model instead).
5. No changes to the compression pipeline itself, pipeline ORDER, or ledger schema beyond the settings table + G1 wiring. This is a UI/UX + configuration-persistence release.
6. No new provider integrations; provider registry remains config/seed-driven.
7. No user accounts, sessions, or login UI; ADMIN_TOKEN remains the single operator credential.

## 8. Release blockers

- B1: Ledger write failures remain visible (token_saver_ledger_write_failures) and any new UI path that could swallow them fails the QA gate (AC-PC-UI hardening precedent).
- B2: Settings allowlist enforced server-side — the UI must not be the only gate on what is writable.
- B3: G1 decision recorded (wired OR labeled benchmark-only) before Settings tab ships pipeline-lane statuses.
- B4: A settings override cannot break in-flight semantics: the request path must read the effective setting once per request (no mid-request flip), verified by QA.
- B5: Secret-handling rules (§3.4) verified by an extended test_ac_a13_secret_handling.py-style gate on every new endpoint.
- B6: /stats, /metrics, /health, and the existing /api/kpis contract unchanged (regression tests pin them).

## 9. Measurable acceptance criteria

Design (owner: @ui-ux-engineer, gate: PM review):

Implementation (owner: @application-developer):

- AC-I4: G1 resolved per §5.4 decision; TOCP/tool-results path either works against an authenticated proxy key in a live-path test, or UI/labels state benchmark-only scope.
